# Экспериментальная архитектура Routeveil

**Статус: проектный контракт интеграции. Этот документ не подтверждает сборку APK, работу на устройстве или отсутствие утечек.**

![Архитектура](<../../assets/architecture.svg>)

## 1. Границы доверия и поток данных

```text
Выбранное приложение или companion :probe (отдельный UID)
  -> per-app маршрутизация Android VpnService
  -> сохраняемый TUN -> стек Onionmasq -> Arti
  -> необязательный IPtProxy -> доступный bridge -> сеть Tor -> HTTPS-сайт

Прямые исключения -> обычная сеть, вне Tor
Основной APK <-> явный протокол companion, защищённый signature-permission
```

Основной APK — Java-приложение Android API 26+, target/compile SDK 36. Backend закреплён: `org.torproject:onionmasq:1.9.1Beta-local-release`. Это beta, а не production-stable. Свой VPN-сервер не требуется, но чужие relays, bridges и транспортные сервисы необходимы.

Оболочка отвечает за политику, интерфейс, жизненный цикл, проверку bridge-строк, маршрутизацию и статусы. Onionmasq предоставляет пользовательский сетевой стек и Arti; его Android-слой запускает IPtProxy для мостов. Второй VPN-service или дублирующий IPtProxy-контроллер не нужен.

## 2. Выбор транспорта

AUTO формирует конечную очередь из пользовательских obfs4/WebTunnel/Snowflake и встроенных Snowflake/obfs4. За одну попытку допускается не более четырёх профилей. Порядок и усечение очереди должны быть видны: пять категорий не обязательно помещаются в четыре позиции. Каждая строка проверяется отдельно, в профиле допускается один тип транспорта, дубликаты удаляются; неподдерживаемая конфигурация отличима от сетевого timeout.

Ошибочный или пустой bridge-профиль не должен превращаться в direct Tor. Режим «Direct Tor» — отдельное явное решение пользователя, а не скрытый fallback AUTO. Встроенные мосты — версионированные данные, не гарантия доступности; может понадобиться ручной импорт.

Обычное «Подключить» останавливается на первом готовом профиле. «Оптимизировать» — отдельное ограниченное сравнение: bootstrap измеряется отдельно от HTTPS-задержки и передачи 64 КиБ через companion. Показываются endpoint, время, ошибки и объём выборки. Малый transfer зависит от TLS, кэша, нагрузки и exit-policy: это приблизительное измерение, не полноценный тест пропускной способности. Бесконечный поиск «самой быстрой цепочки» запрещён контрактом.

## 3. Companion и честность измерений

`:probe` — отдельный установленный APK с другим UID, подписанный тем же сертификатом. Явные компоненты и signature-permission защищают команды и ответы. Во время измерения helper обязательно идёт через Tor и не должен предлагаться как прямое исключение. Проверяются идентификатор запроса, сроки, лимиты байтов и ожидаемый источник; устаревшие ответы отбрасываются. Не создавать доступный другим приложениям сервис запросов к произвольным URL.

В bridge-режиме основной APK исключается из VPN, как в upstream Tor VPN. Для Arti есть защита сокетов; выбранная штатная интеграция IPtProxy не предоставляет такую защиту для всего транспортного пути. Поэтому обычный HTTP-запрос основного APK измерял бы прямую сеть, а не Tor. Отдельный процесс с тем же UID эту проблему не решает.

Если companion отсутствует, подпись не совпадает, запрос завершился timeout или маршрут не подтверждён, результат — **активное Tor-измерение недоступно**, а не выдуманная оценка. Туннель может работать по bootstrap-событиям. Пассивные native-счётчики показывают объём трафика, но не доказывают ёмкость канала. Реальный Tor-egress helper надо проверить на устройстве.

Только действительно наблюдаемый helper challenge может вызвать уведомление с предложением вручную открыть сайт в приложении пользователя. Обычные 403/429 или сетевая ошибка не равны CAPTCHA. Cookies и прохождение challenge не переносятся автоматически между helper и браузером/приложением. Автоматических решателей, кликов CAPTCHA и перехвата учётных данных нет.

## 4. Per-app маршрутизация

Редактируемый DIRECT-набор содержит начальные удобные исключения:

| Приложение | Начальный package identifier |
|---|---|
| Госуслуги | `ru.gosuslugi.gosuslugi` |
| Яндекс Навигатор | `ru.yandex.yandexnavi` |
| Яндекс Go / такси | `ru.yandex.taxi` |
| VK | `com.vkontakte.android` |
| MAX | `ru.oneme.app` |

Проверять фактическую установку пакетов; предустановки не подтверждают идентичность всех редакций приложений. Намеренно очищенный набор не восстанавливать самовольно. Эти исключения раскрывают обычный сетевой адрес и **не являются белым списком оператора РФ**, доменным фильтром или маршрутизацией по странам.

Android allowed/disallowed application lists взаимоисключающие. Задавать их до establish и аккуратно пересоздавать TUN при изменении. Отсутствие вызовов addAllowedApplication означает «все приложения», а не «ни одного». Основной APK исключается для bridges, но не автоматически для direct Tor. Helper не должен наследовать это исключение.

На Android API 26–28 работает системная per-app маршрутизация, однако backend не может использовать connection-owner UID API и возвращает неизвестный UID. Не обещать там изоляцию Tor-цепочек и native-счётчики по приложениям. На API 29+ атрибуцию нужно проверять, а не считать безусловной для каждого потока. Логины, идентификаторы устройства и поведение приложений всё равно могут связывать действия пользователя.

## 5. Жизненный цикл и граница fail-closed

Нужен последовательный автомат состояний, например:

```text
STOPPED -> PREPARING -> BLOCKED_TUN -> BOOTSTRAPPING -> READY
READY -> SWITCHING/BLOCKED_TUN -> BOOTSTRAPPING
любое активное состояние -> BLOCKED_ERROR или явное STOPPED
```

Получить согласие VpnService.prepare, запустить foreground service с уведомлением, один раз инициализировать Onionmasq и обеспечить защищённые backend-сокеты. Native start блокируется и получает владение переданным файловым дескриптором; нужны отдельные worker-потоки и явный учёт владения. Stop не может ждать в том же однопоточном executor, где заблокирован start. Обработать revoke, cancellation, cleanup и запоздалые события.

Пока service жив, контракт требует сохранять блокирующий TUN при переключениях профилей и ошибках. Native backend владеет рабочим fd; простого stop/start недостаточно, чтобы доказать непрерывность блокировки. Нужна согласованная передача между интерфейсами/блокирующий интерфейс и проверка отсутствия прямого fallback выбранных приложений.

Crash, force-stop, смерть service или reboot могут убрать TUN. Системные Always-on и «Блокировать соединения без VPN» — отдельный пользовательский механизм: он способен блокировать и прямые исключения. Нельзя одновременно обещать универсальный глобальный kill switch и неограниченный direct bypass.

Strict Private DNS с заданным hostname несовместим с выбранным backend. Проверять до старта и во время работы; оставаться в блокирующем состоянии с понятной ошибкой. Не менять системную настройку DNS и не уходить незаметно на DNS оператора. IPv4/IPv6 и DNS должны обрабатываться контролируемо; неподдерживаемый UDP не выпускать напрямую. Произвольные UDP/QUIC/VoIP — вне обещанных возможностей.

## 6. Ротация

Автоматическая ротация выключена по умолчанию. Если включена — интервал не менее 60 секунд, без перекрывающихся запросов. `OnionMasq.refreshCircuits()` и `refreshCircuitsForApp(uid)` отказываются от старых цепочек для **новых соединений**. Это не control-port `SIGNAL NEWNYM` C Tor и не гарантия новой личности/IP. Старые TCP-сессии продолжаются; cookies и логины остаются. Смена bridges требует управляемого перехода backend/TUN, не только refreshCircuits.

## 7. Локальная диагностика и добровольная передача

Контракт логирования: два ротируемых JSONL-файла не более 128 КиБ каждый, ограниченное хранение и явная кнопка очистки. Записывать только события и коды из разрешённого набора. Не хранить IP-адреса, URL, bridge-строки, секреты, персональные данные, HTTP-body и сырой native logcat. Не добавлять непроверенный exception text и пользовательские строки в структурированные события. Лимит размера сохраняется и при ошибочных/слишком больших событиях.

Экспорт текста выполняется по инициативе и подтверждению пользователя через Android chooser: непубличный read-only ContentProvider выдаёт временное разрешение выбранному получателю. Автоматической загрузки и собственного сервера логов нет. Пользователь может выбрать чат анализа; это осознанная внешняя передача экспортируемой диагностики, не фоновая отправка. Проверять режим доступа, область URI, жизненный цикл и очистку; не открывать произвольные приватные файлы. Это требования реализации/приёмки, не PASS проверки безопасности.

Telegram — отдельная цель приёмки: подключение, сообщения и media/video с разрешения, отдельно voice/video calls. Не отправлять реальные тестовые сообщения без согласия. Произвольный UDP базовым Tor не поддерживается, поэтому звонки не обещаются даже при работающих тексте и media. YouTube/Instagram/Telegram не должны входить в начальные DIRECT-исключения.

## 8. Ограничения и источники

Обфускация помогает лишь против некоторых способов фильтрации и не разрешает заблокированный адрес при строгом операторском allowlist. Нужен доступный вход и вспомогательные транспортные сервисы. Замеров в сетях операторов РФ здесь нет; универсального обхода не обещаем. HTTPS нужен и после выходного узла Tor.

Routeveil и собственная схема не связаны с брендом Tor Project. См. [лицензии зависимостей](<../../THIRD_PARTY_NOTICES.md>) и [матрицу ожидающих проверок](<testing.md>).
